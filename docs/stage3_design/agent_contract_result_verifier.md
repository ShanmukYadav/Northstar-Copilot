# Agent Contract - Result Verifier
Stage 3 - Design (pulled forward) - v1
Owner: Vishal (drives) - Reviewer: Ankit

## The actual risk

The brief requires query exposure -- the user must see the SQL that produced their answer
(PRD section "in scope"). But the SQL that *executes* in the sandbox and the SQL that's *safe to
show* Sam or Priya are not automatically the same string. A naive approach -- run the
query, show the query -- leaks whatever the execution layer happens to contain: an
absolute path to the sandbox database file, an internal schema prefix used for
row-level isolation, a planner-generated CTE alias like `_tmp_join_ctx_4`, or (worst
case) a connection string if one was ever inlined instead of pre-bound.

**String redaction on the executed SQL is the wrong fix.** Regex-stripping known-bad
patterns is a blocklist, and blocklists miss things -- a new internal alias format, a
different path convention, a debug comment someone added. The design below avoids the
problem structurally instead of trying to catch every leak after the fact.

## Design: two SQL representations, one generated from a controlled AST

1. **`execution_sql`** -- what the sandbox tool actually runs. Never leaves the agent
   boundary. Never logged to a user-facing trace. May reference whatever internal
   structure the sandbox needs.
2. **`display_sql`** -- what the user sees. Generated by parsing `execution_sql` into an
   AST (via a SQL parser, e.g. sqlglot) and **re-emitting it from an identifier
   allowlist** -- every table and column reference is rewritten to its public/logical
   name via a mapping table, and anything not on the allowlist (internal schemas, engine
   hints, generated aliases) simply cannot be re-emitted, because the allowlist doesn't
   contain it. This is a positive-list reconstruction, not a negative-list redaction -- a
   leak would have to be a mapping-table bug, not a missed regex pattern.
3. **Defense in depth, not reliance on step 2 alone**: the sandbox connection is
   pre-bound by the execution environment (fixed DSN, injected at tool-init time, never
   part of any prompt or query string). `execution_sql` therefore structurally cannot
   contain a connection string or file path in the first place -- there's nothing to
   redact because it was never constructible from agent output.

## Contract

```json
{
  "agent": "result-verifier",
  "single_responsibility": "Execute a candidate SQL query in the read-only sandbox, validate the result against sanity and join-grain checks, and produce a user-safe rendering of both the query and the result.",
  "inputs": {
    "question": "string - original user question",
    "candidate_sql": "string - SQL produced by the query-writer agent",
    "schema_context_ref": "string - pointer to the retrieved schema slice used (Chroma doc ids), not the full catalog"
  },
  "outputs": {
    "verification_status": "enum: pass | fail | needs_clarification",
    "sanity_checks": [
      {"check": "string, e.g. 'distinct_order_id_used_for_multiseller_join'", "result": "pass | fail", "detail": "string"}
    ],
    "display_sql": "string - AST-reconstructed, allowlist-only identifiers, safe to render to Sam/Priya",
    "result_summary": {
      "row_count": "integer",
      "columns": ["string"],
      "sample_rows": "array, capped at N rows, values only - no internal metadata"
    },
    "confidence_signal": {
      "parses": "boolean - deterministic SQL-parser result",
      "schema_grounded": "boolean - every identifier resolved against real schema, no hallucinated column/table",
      "sanity_checks_passed": "boolean"
    }
  },
  "tools_allowed": [
    "sql_sandbox_execute (read-only, parameterized, timeout-bound, pre-bound connection)",
    "schema_lookup (vector store, read-only)"
  ],
  "tools_forbidden": [
    "any write/update/delete capability",
    "raw filesystem access",
    "direct exposure of execution_sql or the sandbox connection object to any downstream agent or the user-facing response"
  ],
  "model_tier": "cheap-tier (deterministic checks + AST rewrite are largely non-LLM; only ambiguous sanity-check judgment calls escalate to the narrator agent's tier, not this agent's)"
}
```

## Why confidence_signal is structural, not a model-reported number

Per PRD section 7 (confidence definition), escalation to Devon's team is triggered by these
three deterministic booleans, not by asking a model how sure it feels. A model's
self-reported confidence isn't grounded in anything verifiable; a parser result and a
schema-membership check are. The empirical threshold for how these combine into an
escalation decision is set in Stage 7 against the golden set -- this contract just
guarantees the signal itself is trustworthy input to that decision.

## What this does NOT yet solve (flagged honestly, not glossed over)

- Row-level or column-level data sensitivity (e.g. should sample_rows ever mask a
  column) isn't addressed here -- no PII-bearing columns were identified in the Olist
  schema during Stage 2 profiling, so this is deferred rather than solved, and should be
  revisited if scope ever expands beyond Olist.
- The identifier-allowlist mapping table itself needs an owner and a review step when
  the schema changes -- this is a registry concern, tied to the agent registry design
  (Stage 3, still open).
